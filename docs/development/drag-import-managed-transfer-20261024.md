# 拖入持续忙碌：改用 DeskBox 传输引擎

## 故障与取舍

合并 1.5.9 后，用户拖入文件时提示“上一次导入还在进行中”。日志显示首笔导入进入 Windows `IFileOperation.PerformOperations()` 后没有进展，后续拖入被忙碌检查拒绝。45 秒看门狗能结束等待并释放忙碌状态，但原生线程仍未返回。

现场线程检查发现，Shell 进度窗口线程在获得焦点时进入 `ImmSetActiveContext`、`CtfImeAssociateFocus` 和讯飞输入法的 `iFlyTsfIme.dll` / `iflyclient.dll`，随后停在等待中；两笔文件传输线程则在 COM 等待。主界面线程仍能处理消息。另用一个临时文本文件，通过现有 `WM_DROPFILES` 入口复现：导入开始后源文件仍在，目标文件没有出现。

用户选择方案 A：普通拖入改用 DeskBox 已有的托管传输引擎，使用格子内的进度、取消和结果反馈。方案 B（仅隐藏 Shell 进度窗口）未采用，因为它仍依赖同一 Shell UI，在出现冲突或错误窗口时可能再次进入输入法路径。

## 修改范围与行为

- 普通文件导入的共享入口及两条文件夹导入路径不再请求 Shell 进度。主表面、文件夹卡片、叠放以及粘贴共用这些入口。
- 复制、移动、快捷方式意图和 OLE 完成回执的安全规则保持原有处理。没有通过清除忙碌标志、缩短看门狗或自动重试来绕过仍可能运行的传输。
- 格子已有的传输引擎提供字节和项目进度、取消、已完成项目结算、部分失败结果及移动历史。正在传输的源文件仍受传输会话保护。
- 重名项目按现有规划生成 `文件名 (2)` 等可用名称。若规划后发生竞争，传输拒绝覆盖已有目标；发生错误时保留已完成项目，并通过现有本地化失败反馈说明结果。
- 普通拖入不再依赖 Windows 的传输进度、冲突或错误窗口。需要权限的源文件可能失败并保留原件，不会自动退回存在阻塞风险的 Shell 路径。
- Windows Shell 传输实现继续保留，显式请求 Shell 或系统提权的入口仍可使用。合并提交 `c16466b6` 完整保留此前实现，可作对照和备用。
- 未更改、关闭或卸载输入法，也未改变防护软件配置。
